# Осавул

Детермінований статичний аналізатор для коду, згенерованого ші: задум
інструмента, що дає ші-агентам миттєвий зворотний зв'язок ще до того, як код
побачить людина.

## Проблема

Донедавна індустрія оптимізувала написання коду, бо вузьким місцем був час
розробника, а класичні інструменти якості розраховані на світ, де людина пише
небагато і спокійно чекає на перевірку в ci.
Тепер ші-агенти генерують код значно швидше, ніж його можна перевірити, тож
вузьким місцем стали верифікація й архітектурна ентропія.
Код, згенерований ші, оптимізований локально: він вирішує поточний запит і
виглядає правдоподібно.
Проте глобально він руйнівний: дублює логіку, тягне неіснуючі або небезпечні
залежності, породжує тести-пустушки, які нічого не перевіряють, і поступово
розмиває межі системи.
Кожне таке рішення окремо здається прийнятним, а разом вони непомітно псують
кодову базу.

## Що ми будуємо

`osavul` задумано як імунну систему для кодових баз епохи ШІ.
Це не ще один лінтер і не просте перенесення наявного інструмента на rust: мета
в тому, щоб виявляти ризики, які стосуються системи загалом, а не лише окремого
рядка чи стилю файла.
Такі ризики охоплюють небезпечні залежності, порожні тести та поступове
руйнування архітектурних меж.

## Принципи

- **Детермінізм замість ймовірності.** Перевіряти ймовірнісний код лише іншою
  моделі дорого, повільно й без гарантій, тому фундамент довіри має бути жорстким,
  точним і відтворюваним статичним аналізом.
- **Зворотний зв'язок для агентів, а не дашборд сорому для людей.** Агент має
  отримати точну причину ризику й вимогу виправити код до того, як його побачить
  людина.
- **Швидкість у мілісекундах, локально.** Ціль у тому, щоб аналіз працював на
  власній машині та був непомітною частиною кожного збереження файла чи виклику
  інструмента агентом.
- **Нульовий шум.** Краще пропустити дрібну стилістику, ніж реальний вектор
  атаки чи архітектурну діру: кожне спрацювання має бути важливим і вимагати
  дії.

## Що аналізатор має ловити (заплановано)

Нижче перелічено заплановані напрями перевірки, а не готові можливості:

- ін’єкція запитів та підміна інструкцій;
- перехоплення вигаданих пакетів і галюциновані залежності;
- тести-імітації;
- дублювання логіки;
- архітектурні прогалини та розмивання меж.

## Платформи

Підтримуються Ubuntu Linux (`x86_64-unknown-linux-gnu`), Windows (`x86_64-pc-windows-msvc`) і macOS на Apple Silicon
(`aarch64-apple-darwin`); інші не є цільовими. Рішення й межі гарантій — в
[ADR-0003](docs/architecture/decisions/0003-target-platforms.md), команди перевірки — у
[політиці тестування](docs/testing-policy.md#платформи-й-перевірка-цілей).

## Доступна команда

```sh
osavul check <файл-або-тека>
```

Перевіряє поточний вміст файла `.ts` (разом із `.d.ts`) чи `.rs` або теки на диску (рекурсивно; пропускає
`.git`, `node_modules` і вкладені `target`, на явний корінь пропуски не діють).
Git не потрібен. Явний файл з іншим суфіксом — помилка. Знаходить порожні тести
(Rust: `#[test]` без вмісту в тілі; TypeScript: прямий виклик `it` чи `test` з рядком і
функцією з порожнім блоком; пробіли й коментарі вмістом не є) і друкує
по рядку на знахідку: `<шлях>:<рядок>: empty-test: тест порожній: напишіть перевірку в тілі тесту або видаліть його`.
Шлях — написання аргументу (для теки — аргумент, `/` і відносний шлях файла),
порядок — за байтами шляху, номером рядка й ідентифікатором правила.

```text
./src/a.rs:2: empty-test: тест порожній: напишіть перевірку в тілі тесту або видаліть його
./src/b.ts:7: empty-test: тест порожній: напишіть перевірку в тілі тесту або видаліть його
```

Рядок — це `fn` для Rust і ідентифікатор `it`/`test` для TypeScript.

Коди завершення: `0` — усе перевірено, знахідок немає; `1` — є знахідки; `2` —
помилка (має пріоритет). Помилка аргументів, шляху чи переліку теки лишає stdout
порожнім. Помилка окремого файла (читання, UTF-8, розбір) прибирає лише його
знахідки: причину зі шляхом видано в stderr, решта файлів перевіряється. Для
відібраних `.rs` (і лише для них) потрібен локально встановлений toolchain 1.100.0: синтаксис
перевіряє `rustc -Z parse-crate-root-only`.

```sh
osavul complexity <ревізія> [--metric <cyclomatic|cognitive|loc>]
```

Вимірює складність звичайних файлів `.ts` (разом із тестами й
`.d.ts`) у дереві одного коміту за методикою `ts-cyclomatic` версії 1 (типово, `--metric cyclomatic`) або
`ts-cognitive` версії 1 (`--metric cognitive`; у записах файлів поле
`cognitive` замість `cyclomatic`) або розмір коду за `ts-loc` версії 1 (`--metric loc`; поле `loc` —
кількість рядків із кодом без порожніх і коментарів) і друкує один компактний JSON у stdout. Потрібен локальний Git; команду можна запускати
з будь-якого підкаталогу репозиторію, вимір охоплює весь коміт. Індекс, робоче
дерево й невідстежувані файли на результат не впливають. Коди завершення:
`0` — повний звіт, `1` — неповний звіт (JSON усе одно у stdout, `total` — `null`),
`2` — помилка аргументів, Git, коміту чи інвентарю (stdout порожній, причина в
stderr). Правила підрахунку й контракт звіту — у
[Звіті складності](docs/domain/entities/complexity-report.md).

```sh
osavul complexity --path <файл-або-тека> [--metric <cyclomatic|cognitive|loc>]
```

Той самий звіт для поточного вмісту на диску: вказаного файла `.ts` або всіх
звичайних файлів `.ts` теки (рекурсивно, разом із тестами, `.d.ts`,
незакоміченими й невідстежуваними файлами; `.git`, `node_modules` і символьні
посилання всередині теки пропускаються). Git не потрібен. Шляхи в звіті для теки
відносні до її кореня, `sha` дорівнює `null`, `scope.input` — `file` або
`directory`. Коди завершення: `0` — повний звіт (тека без `.ts` дає `total: 0`),
`1` — неповний звіт (файл не читається, не є UTF-8 або має синтаксичну помилку;
JSON у stdout), `2` — відсутній шлях, явний файл не `.ts`, помилка обходу або
аргументів (stdout порожній). Опція `--metric` діє так само, як для коміту; вона стоїть лише в кінці виклику,
невідоме значення, повтор чи відсутнє значення — помилка аргументів (код `2`).
Одиночний операнд `osavul complexity <x>` завжди означає ревізію.

```sh
osavul duplication <ревізія>
osavul duplication --path <файл-або-тека>
```

Показує дублювання коду у файлах `.ts` (разом із тестами й `.d.ts`) за методикою
`ts-duplication` версії 1: які блоки повторюються, де лежать усі входження, скільки
рядків і блоків задубльовано та яка їхня частка. Входи, відбір файлів, шляхи й
`sha` такі самі, як у `complexity`; один операнд завжди означає ревізію. Коди
завершення: `0` — повний звіт, `1` — неповний (JSON у stdout, `total` — `null`,
а числа решти файлів — нижня межа покриття), `2` — помилка аргументів, Git чи
інвентарю (stdout порожній). Наявність дублів на код не впливає. Правила — у
[Звіті дублювання](docs/domain/entities/duplication-report.md).

```sh
osavul coverage <ревізія> --lcov <файл> [--lcov <файл>…] [--tests <шлях>…]
osavul coverage --path <тека> --lcov <файл> [--lcov <файл>…] [--tests <шлях>…]
```

Показує покриття рядків і гілок у файлах `.ts` за готовими звітами LCOV (методика
`ts-coverage` версії 1); тести Осавул не запускає й покриття не вимірює. Кожен
`--lcov` задає один звіт (потрібен хоча б один; шлях відносно поточної теки), а
`--tests` — один чи кілька шляхів від кореня (кореня репозиторію для ревізії або
вказаної теки), що є тестами й не входять у покриття; опції можна повторювати.
Відбір файлів, `sha`, `scope`, шляхи й причини `error` такі самі, як у `complexity`.
Коди завершення: `0` — повний звіт (низьке покриття на код не впливає), `1` —
неповний (звіт не узгоджений із кодом; JSON у stdout, `total` — `null`), `2` —
помилка аргументів, Git, коміту, шляху чи читання LCOV (stdout порожній). Правила —
у [Звіті покриття](docs/domain/entities/coverage-report.md).

## Чим це відрізняється

Ринок інструментів поділений на кілька категорій, і кожна закриває свою частину
завдання: класичні інструменти якості й безпеки дають широке покриття, швидкі
сучасні аналізатори охоплюють переважно синтаксис, форматування чи класичну
безпеку застосунків, ймовірнісні ші-рецензенти допомагають на етапі pull
request, а засоби безпеки ланцюга постачання зосереджені на вужчих ризиках. Це
різні компроміси, і кожен із них доречний у своєму місці. Ніша `osavul` за
задумом полягає в поєднанні швидкості й легкості rust-бінарника, глибини
детермінованого статичного аналізу та аналізу потоків недовірених даних та роботи безпосередньо в циклі
ші-агента, зокрема через MCP-сервер.

## Північна зірка

Повернути інженерам впевненість у кодовій базі, навіть коли 90% коду написали
автономні агенти.

## Quality gate

```sh
osavul gate <база> <ревізія>
```

Порівнює два коміти локального Git (ревізії розв'язуються як у `complexity`; запуск із будь-якого підкаталогу репозиторію) і відповідає, чи не погіршилася ревізія: для кожного правила `check` і для `duplication` сума в ревізії не має перевищувати суму в базі. Індекс, робоче дерево й невідстежувані файли не впливають. Вивід — рядок стану кожної умови, подробиці порушених і `gate: пройдено` або `gate: не пройдено`. Коди: `0` — пройдено, `1` — не пройдено, `2` — вердикт визначити неможливо (аргументи, Git, ревізія чи будь-який файл; stdout порожній, причини в stderr). `rustc` потрібен лише коли відібрано файли `.rs`. Докладніше — [Quality gate](docs/domain/entities/quality-gate.md).
