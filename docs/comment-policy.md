# Політика коментарів

Коментар пояснює те, чого читач не відновить із назв, типів і самого коду: чому зроблено саме так, який контракт
чи інваріант треба зберегти, де межі застосовності. Для кожного коментаря діє одне запитання: що читач утратить,
якщо його видалити? Якщо нічого, коментаря тут не місце.

Відсутній коментар кращий за той, що переказує код: переказ нічого не додає і застаріває разом зі зміною коду.

## Три види коментарів

| Вид   | Для чого                                                             |
| :---- | :------------------------------------------------------------------- |
| `//!` | Призначення модуля та його межі; пишеться на початку файла           |
| `///` | Контракт елемента: те, що має знати той, хто його викликає чи змінює |
| `//`  | Неочевидне всередині реалізації: причина, обмеження, обхід           |

Опис контракту функції, типу, поля чи варіанта оформлюється як `///`, а не `//`: інакше його не покажуть
`cargo doc` і підказки редактора. Це стосується й приватних елементів.

Блокові коментарі `/* */` і `/** */` не використовуються.

## Коли коментар потрібен

* **Модуль.** Кожен файл у `src/` починається з `//!`: одне-три речення про те, за що модуль відповідає і чого
  не робить.
* **Контракт, якого не видно з сигнатури:** порядок результатів, значення порожнього результату, одиниці виміру,
  припущення про вхід, умови помилки чи паніки.
* **Інваріант**, порушення якого компілятор не помітить.
* **Причина** неочевидного рішення, обхід помилки, особливість зовнішньої системи (Git, парсера, компілятора,
  операційної системи).
* **Правило методики**, коли з коду видно, що рахується, але не видно, чому саме так.
* **`unsafe`:** над блоком коментар `// SAFETY:` пояснює, чому він коректний.

Опис кожного `pub`-елемента не обов’язковий. Якщо ім'я та сигнатура все пояснюють, `///` не пишеться.

## Чого не писати

* Переказу коду, повтору назви функції, змінної чи типу.
* Опису параметрів і результату, який повторює їхні типи.
* Закоментованого коду: попередні версії зберігає git.
* Історії змін, авторства, дат і номерів задач замість пояснення.
* `TODO` чи `FIXME` без названої перешкоди або умови, за якої це треба зробити.

## Приклади

```rust
// Погано: переказує сигнатуру.
/// Приймає шлях і повертає список рядків.
fn read_lines(path: &Path) -> Result<Vec<String>, ReadError>

// Добре: каже те, чого сигнатура не показує.
/// Порядок рядків збігається з файлом; порожній файл дає порожній список, а не помилку.
fn read_lines(path: &Path) -> Result<Vec<String>, ReadError>
```

```rust
// Погано: пояснює очевидне.
// Збільшуємо лічильник.
total += 1;

// Добре: пояснює причину.
// Гілка `else if` має фіксований приріст: вкладеність уже врахував початковий `if`.
total += 1;
```

## Оформлення

* Мова коментарів українська. Ідентифікатори, команди, шляхи, значення та усталені маркери (`SAFETY`, `TODO`) не
  перекладаються. Назви в коді беруться в зворотні лапки.
* Повні речення з великої літери та з крапкою. Перше речення `///` самостійно називає суть.
* Секції `# Errors`, `# Panics`, `# Safety` додаються лише тоді, коли є що сказати понад тип результату. Їхні
  заголовки лишаються англійськими за звичаєм Rust.
* Довжина рядка така сама, як у коду; `rustfmt` не переносить коментарі за вас у всіх випадках, тож це
  перевіряє автор.
* Директиви для інструментів і shebang не є коментарями в сенсі цієї політики.

## Коментар і документація

Коментар пояснює конкретне місце коду. Поняття домену, потік даних і причини архітектурних рішень живуть у
`docs/` за [політикою документації](documentation-policy.md). Коментар може посилатися на такий документ шляхом,
а не повторювати його. Коментарі в тестах про інваріанти, які ті охороняють, визначає
[політика тестування](testing-policy.md).

## Оновлення

Зміна поведінки оновлює або видаляє пов'язаний коментар у тому самому коміті. Коментар, що суперечить коду, є
дефектом.

## Рецензування

Рецензент питає: чи дає коментар щось понад код? Чи не бракує пояснення там, де рішення неочевидне? Чи
оформлено контракт як `///`? Чи не застарів коментар після зміни? Наявність коментарів автоматично не
перевіряється.
